## 1. 定位与原则

### 1.1 一句话

> **清洁架构定依赖方向；DDD-light 定业务边界；模块化单体定同仓协作与演进节奏。**

| 痛点 | 回答 |
| ---- | ---- |
| 规则散落在接口 / 存储层 | 收敛到领域服务 |
| 多入口复制业务逻辑 | 领域复用；差异只在编排 |
| 跨域乱引用 | 只依赖对方公开面；类型随域走 |
| 过重 DDD 拖慢交付 | 保留上下文与契约，不强制完整战术仪式 |

### 1.2 核心原则

1. **依赖向内**：编排 → 领域公开面 → 领域内部 → 基础设施。  
2. **领域无传输细节**：无路由、无协议 DTO、无请求上下文解析。  
3. **编排不做业务规则**：编排负责身份上下文、一致性边界、跨域组合、DTO 映射。  
4. **契约优于实现**：对外暴露服务接口与领域错误；实现进私有区。  
5. **类型随域**：跨边界类型放在本域 `pkg/shared`（勿平铺域根、勿上收仓级）。  
6. **横切靠外**：幂等 / 事务等由编排包裹；领域保持可组合、可单测。  
7. **战术按需升级**：先有边界与可测规则，再按痛点加重 DDD 战术。

## 2. 仓库骨架

```text
repo/
├── apps/              # 编排入口（可多入口）
│   └── <entry>/internal/
│       ├── bootstrap/ handler/ usecase/
│       ├── policy/    # 跨域编排策略（可组合多个领域契约）
│       └── support/   # 浅层错误等入口工具（非业务类型）
├── domains/           # 有界上下文（类型与契约同模块）
├── script/            # 构建 / 迁移等（按需）
└── ui/                # 客户端经网络调编排，不直连领域
```

| 层 | 职责 |
| -- | ---- |
| `apps/*` | 启动、接口适配、UseCase 编排、跨域策略、依赖装配 |
| `apps/*/internal/policy` | 跨域编排策略：需要组合多个领域契约的授权/一致性判断 |
| `apps/*/internal/support` | 会话 / 错误投影等浅层入口工具；非业务类型，不依赖领域 |
| `domains/*` | 规则、持久化、契约、本域 `pkg/shared` |

多入口时：**差异在路由、权限与用例组合，不在领域规则复制。**

## 3. 分层与依赖

### 3.1 请求链路

```text
外部请求 → Handler（适配）→ UseCase（编排）→ Domain Service（规则）→ Repo → 存储
```

### 3.2 与 Clean Architecture 的对应

| Clean 层 | 落点 |
| -------- | ---- |
| Entities | 本域 `pkg/shared/entity` |
| Domain | `internal/service` + `service_contract` |
| Application | `apps/*/usecase` |
| Adapters | handler / repo / provider |
| Frameworks | Web / ORM / 缓存等（可替换） |

刻意把「领域规则」与「应用编排」拆开，避免领域依赖会话、幂等等应用横切。

### 3.3 依赖硬约束

```text
apps ──► 领域公开面（契约 + pkg/shared + provider）
              │
              ▼
         领域 internal（仅本模块）
```

| From | 可以 | 禁止 |
| ---- | ---- | ---- |
| 编排（handler / usecase / policy / middleware） | 领域公开面、入口 support、基础设施 | 任意域 `internal/**` |
| 领域 | 基础设施抽象；其他域的**契约与 `pkg/shared`**（按需） | `apps/*`、入口 support / policy、外域 `internal` |
| 入口 `policy` | 多个领域**契约与 `pkg/shared`** | 任意域 `internal/**`、handler / usecase 实现 |
| 入口 `support` | 浅层错误投影、协议边界工具 | `domains/*`、handler / usecase / policy 实现 |

**口诀**：领域依赖了编排或外域私有实现 → 打回；support 依赖了领域 → 打回。

## 4. 领域模块

### 4.1 标准骨架

```text
domains/<context>/
├── pkg/shared/            # 本域公开类型（随模块发布）
│   ├── entity/
│   ├── input/
│   ├── output/
│   └── enums/
├── provider/              # 唯一公开装配入口
├── service_contract/      # 对外接口 + 领域错误
├── internal/              # 私有
│   ├── repo_contract/     # 仓储端口（仅供本域 service 使用）
│   ├── repo/              # 仓储实现 + 非导出持久化模型 + mapper
│   └── service/           # 领域服务实现
├── event/                 # 可选
└── <algo>/                # 可选：编排必须直接引用的策略
```

| 包 | 可见性 | 说明 |
| -- | ------ | ---- |
| `pkg/shared/*` | 公开 | 跨边界类型；拆模块时一并带走 |
| `service_contract` | 公开 | 能力接口 + 业务错误 |
| `provider` | 公开 | 组装并对外给出 Module |
| `internal/repo_contract` | 私有 | 仓储端口；service 只依赖它，不依赖实现 |
| `internal/*` | 私有 | 禁止跨模块引用 |

默认实现放 `internal/`。仅当编排或 provider 必须引用类型时，才把策略包提到域根。

### 4.2 本域 pkg/shared

路径：`domains/<context>/pkg/shared/...`。  
**不要**平铺在域根，也**不要**上收成仓级业务类型库。

跨域需要对方类型 → 依赖对方模块的 `pkg/shared`。  
两域争改同一结构体 → 先怀疑边界或做防腐，而不是再抽「公共模型」。

入口 `support` 只放浅层错误与协议边界工具，不是业务类型库；领域不得依赖 support。

### 4.3 双实体

| | 领域实体 | 持久化模型 |
| - | -------- | ---------- |
| 位置 | `pkg/shared/entity` | `internal/repo`（非导出类型；跨仓储复用时才提为 `internal/model`） |
| 用途 | 跨边界传递、表达业务含义 | 对接存储 |
| 转换 | 仅在仓储适配内完成 | |

跨边界只返回公开实体；持久化模型不泄漏出私有区。

## 5. 编排入口

```text
apps/<entry>/
└── internal/
    ├── bootstrap/     # 初始化 + 领域装配 + 挂路由
    ├── handler/       # 薄适配
    ├── usecase/       # 编排
    ├── policy/        # 跨域编排策略
    ├── middleware/
    └── support/       # 本入口浅层错误等
```

| 角色 | 做 | 不做 |
| ---- | -- | ---- |
| Handler | 路由、绑定、调用 `Execute` | 业务分支、多域组合 |
| UseCase | 身份上下文、浅校验、映射、调契约；写路径包一致性边界 | 复制领域规则 |
| Policy | 跨域授权、最后一名超管等需组合多域的策略 | 协议解析、存储细节、单域不变量 |
| Support | 浅层错误投影、会话/协议边界工具 | 业务规则、依赖领域 |

**两类 Input**：协议 Input 在 usecase；领域 Input 在本域 `pkg/shared/input`。UseCase 负责转换。

## 6. 规则归属

| 问题 | 放哪 |
| ---- | ---- |
| 聚合完整性、状态机、唯一性、字段格式等 | Domain |
| 换入口仍成立的规则 | Domain |
| 跨域步骤编排 | UseCase |
| 会话 / 幂等 / 事务边界 | UseCase |
| 跨域授权、最后一名超管、操作者相关不变量 | UseCase 或入口 `policy` |
| 协议空值、分页默认 | UseCase（浅层，不替代领域规则） |

**口诀**：换入口仍成立 → Domain；依赖本次会话 / 幂等 / 多域组合 → UseCase / policy。

```text
新逻辑 → 仅单域规则？ → Domain
       → 跨域 / 会话 / 协议横切？ → UseCase
       → 需组合多个领域契约的授权/一致性策略？ → policy
```

## 7. 跨域与装配

**允许**：UseCase / policy 组合多个契约；装配期注入其他域契约；按需事件。  
**禁止**：碰外域 `internal`；复制外域持久化模型；新建仓级业务类型库。

**归属三问**

1. 换入口是否仍同一规则？→ 是则偏领域  
2. 是否必须深入两个上下文内部？→ 是则拆契约，编排组合  
3. 配置还是运行时实例？→ 常属不同上下文，勿揉成万能模型  

**两级装配**：域内 `Provide` 产出 Module → 入口 bootstrap 接到 UseCase / Handler。  
横切能力注入 UseCase，不穿透进领域实现。

---

## 8. 写路径与错误

```text
Handler → UseCase →（幂等 / 事务等一致性边界）→ DomainService
```

领域错误在契约中定义稳定语义；编排只处理编排失败，不改写业务含义。  
跨域策略错误定义在入口 `policy` 包；浅层协议 / 会话错误放在入口 `support`。

## 9. 与 MVC / 经典 DDD

### 9.1 vs MVC

#### 要解决的主矛盾不同

| | MVC（及常见「MVC + Service」三层） | 本方法（Clean + DDD-light） |
| - | -------------------------------- | --------------------------- |
| 经典目标 | **界面与数据的分离** | **业务策略与交付入口的分离** |
| 典型场景 | 页面驱动、以表单 CRUD 为主 | 多入口 API、规则复杂、领域需长期复用 |
| 成功标准 | 页面可维护、交互清晰 | 规则可测、可复用、依赖可评审 |

客户端继续用 MVC / MVVM 完全正常。服务端真正的痛点，往往不是「没有 Service」，而是：

> Controller 变薄之后，**Service 变成上帝类**：一个 Service 注入大量 Repo，跨表 / 跨模块交叉读写，规则、流程、持久化搅在一起。

本方法针对的正是这种「入口瘦了、服务胖了」的结构性膨胀。

#### 结构对照

| 维度 | 典型 MVC / 三层 | 本方法 |
| ---- | -------------- | ------ |
| 主分离轴 | Controller / Service / Model(Repo) | 编排 / 领域 / 基础设施 |
| Controller / Handler | 可薄；薄了不等于架构健康 | 极薄：绑定与委托 |
| **Service** | **易成上帝类**：流程 + 规则 + 多 Repo 交叉 | 拆成 **UseCase（编排）** 与 **Domain Service（单域规则）** |
| 仓储使用 | 任意 Service 可注入多 Repo，边界靠自觉 | 仓储留在领域私有区；跨上下文只经契约，不经 Repo |
| Model | 常混数据 + 持久化 + 部分规则 | 持久化私有；跨边界用本域公开实体 |
| 业务边界 | 常按页面 / 接口 /「某某 Service」切 | 按有界上下文切 |
| 多入口 | 易复制或继续堆进大 Service | 领域复用；入口只换编排 |
| 依赖方向 | 常无强制 | **依赖向内**为硬约束 |

#### 上帝类 Service 为何会出现

1. **按接口堆方法**：新接口就在「对应 Service」里加一段，Service 随接口数膨胀。  
2. **用 Repo 当集成点**：跨表协作不经明确边界，直接在 Service 里注入对方 Repo。  
3. **编排与规则不分**：事务、校验、状态机、查库全写在同一类。  
4. **缺少有界上下文**：没有「哪些概念不能进这个 Service」的硬约束。  

结果是：Controller 看起来很干净，系统复杂度全部沉到 Service——更难测、更难拆、更难复用。

#### 职责落点

| 职责 | MVC / 三层常落点 | 本方法落点 |
| ---- | ---------------- | ---------- |
| 参数绑定 / 响应映射 | Controller | Handler |
| 跨模块流程、身份、幂等、事务 | 大 Service | UseCase（编排） |
| 单上下文不变量 / 状态机 | 同一大 Service | Domain Service |
| 跨上下文协作 | Service 里交叉调多 Repo / 多 Service | 只调对方**契约**；组合放在编排 |
| 持久化细节 | Service 直持多 Repo | 领域私有仓储；不对外暴露 |

#### 优缺点

**MVC / 三层优点**

- 概念少、路径短，上手快  
- 小系统、以存取为主时交付快  
- Controller 变薄后，短期内「看起来很干净」  

**MVC / 三层缺点**

- **Service 上帝类**：方法与依赖持续膨胀  
- **Repo 交叉**：跨边界协作靠直接掏仓储，有界上下文名存实亡  
- 多入口时规则易复制，或继续汇入同一个大 Service  
- 纯业务规则难单测，常与事务、多表访问绑死  

**本方法优点**

- 用「编排 vs 领域」拆开上帝类的两种职责  
- 跨上下文禁止 Repo 交叉，只能走契约  
- 规则可单测、可复用；依赖可评审  

**本方法缺点**

- 前期概念与样板更多（Handler → UseCase → Domain）  
- 需要统一「规则放哪 / 编排放哪」，否则易出现空 UseCase 或胖 Domain Service  
- 若偷建仓级业务类型库，仍会重新耦合  

#### 如何选择 / 如何迁移

| 信号 | 更合适 |
| ---- | ------ |
| 单入口、简单存取、生命周期短 | MVC / 三层往往够用 |
| 多入口、规则复杂、Service 已成上帝类、Repo 交叉严重 | 本方法 |
| Controller 已瘦，但 Service 难测、难拆 | 优先拆编排与领域，而不是再抽「公共 BaseService」 |

迁移顺序（方法论）：

1. **按有界上下文切开上帝 Service**（先定边界，再搬代码）  
2. **跨上下文的 Repo 注入改为契约调用**；跨上下文流程升到编排  
3. **单上下文规则留在 Domain Service**；入口保持薄  

先改目录名、不改「谁持有哪些 Repo」，通常无效。

**共存**：客户端 MVC/MVVM + 服务端本方法，是常见且健康的组合。

### 9.2 DDD-light

**采用**：有界上下文、统一语言、服务契约、域内仓储、按需事件 / 策略。  
**弱化**：显式聚合根、跨层公开仓储、默认全域事件、CQRS/ES、繁琐值对象。

| 经典 | 本方法 |
| ---- | ------ |
| 富聚合根 | 公开实体 + Service 守不变量（可渐进变富） |
| 仓储作跨层端口 | 仓储私有，对外只有 Service |
| Shared Kernel | 类型在本域 `pkg/shared`，不上收仓级 |
| 用例只在 Application | Domain Service + App UseCase 拆分 |

## 10. 演进：领域模块独立发布

同仓协作是起点。领域从第一天就是独立模块（含 `pkg/shared`），终局整模块拆出，由消费方以标准依赖方式引入。

```text
阶段 1  同仓工作区联动开发
阶段 2  领域独立发版
阶段 3  编排侧用标准依赖引用领域模块
```

依赖方向不变，只变「模块从哪解析、如何发版」。  
公开面始终是：契约、provider、本域 `pkg/shared`；`internal` 永不当跨模块 API；禁止再抽仓级业务类型模块。

| 更宜留在同仓 | 更宜独立发布 |
| ------------ | ------------ |
| 契约 / 类型剧烈抖动 | 公开面已稳定 |
| 消费方少且同团队 | 多入口 / 多仓消费 |
| 本地联调是主要矛盾 | 发布节奏互相阻塞 |

**口诀**：先有界、后版本、再拆仓；标准依赖引用是目标，本地工作区只是加速器。

## 11. 检查清单与反模式

### 新领域

1. 写清上下文与非目标  
2. 建 `pkg/shared`、契约、`internal`、provider  
3. 纳入依赖清单；补领域单测  
4. 入口装配接线  

### 新接口

1. 规则归领域，还是先补契约？  
2. UseCase（写路径接一致性边界）+ 薄 Handler + 装配  
3. 跨域授权 / 操作者相关不变量放 `policy`，不要塞回领域  

### 禁止

1. Handler 直访仓储或写存储细节  
2. Domain 依赖请求上下文  
3. UseCase 复制领域校验  
4. 跨域引用 `internal`  
5. 仓级业务类型库，或把编排塞进 `pkg/shared`  
6. Domain 依赖入口 `support` / `policy` 或 `apps/*`  
7. 领域私自接管全局事务 / 幂等  
8. `support` 依赖 `domains/*`，或把业务规则放进 `support`

## 附录：最小心智模型

```text
编排：怎么接请求、怎么组合多域、怎么保证写一致
领域：什么合法、状态怎么变、怎么存
类型：在本域 pkg/shared，随模块走
```

方法论管原则与边界；工程约定管目录与技术选型；规格管业务；代码与测试是真源。
